# Privacy Policy for NetSpeedTray

Last Updated: October 20, 2026

This privacy policy outlines how NetSpeedTray handles information. As an open-source project created by a single developer, transparency and user privacy are top priorities.

### Data Collection and Usage

**NetSpeedTray does not collect, store, or transmit any personal data or network traffic content.**

The application is designed to be completely self-contained on your computer. It does not include any analytics, telemetry, advertising, or crash-reporting services.

- **Network Monitoring:** The application monitors your network adapters locally to calculate your current upload and download speeds. It measures the *volume* of traffic (bytes per second) - it never inspects the *content* of your traffic. This information is **only displayed to you** on the widget and is **never sent to any server**.
- **Network Identity (optional):** If you enable the network-identity indicator, NetSpeedTray can show the Wi-Fi **band** (2.4 GHz / 5 GHz) and, optionally, the **network name (SSID)** on the widget. The band is read from your wireless adapter locally and needs no permission. The SSID is different: **Windows only reveals the network name to apps that have Location access**, so enabling the "Network name" option requires you to turn on Windows Location. This is a **Windows privacy gate, not GPS or geolocation** - NetSpeedTray does not use your position, and reads the network name **locally only to display it on the widget**. Like everything else here, the band and SSID are **never stored to the history database and never transmitted**.
- **Latency probe:** To show how responsive your connection is, NetSpeedTray sends small ICMP echo requests ("pings"). The probe is on by default and can be turned off in Settings - that takes effect at once: no further ping is sent, to your router or to a public host, until you turn it back on. By default its only target is your own **default gateway** (your router): a burst of four every 3 seconds, about 1.3 packets per second. Normally those pings stay on your local network; but while a VPN is connected, the default gateway Windows reports can be the VPN's own gateway, reached through the tunnel. Pinging a public host (for true internet latency, `1.1.1.1` unless you change it) is a separate setting that is **off by default**; when you turn it on, the same ~1.3 packets per second also go to that host. If you type a host *name* rather than an address, Windows looks it up through your normal DNS once per burst (every 3 seconds) - so your DNS server sees that name. The on-demand **Check connection** sheet in the Monitor sends 20 pings, 200 ms apart, to your router and - only if the public host is enabled, or you tick "Also check the internet" in that sheet, which names the host - 20 to the public host. That tick is a one-off: it is not saved, and the check's results are not saved either (they stay on screen until you copy them or close the sheet). Every echo carries the same fixed 12-byte payload, the text `netspeedtray`, identical on every computer - nothing that identifies you or your machine. The round-trip times and loss rates of the standing probe are stored in the local history database like the other statistics, and are never transmitted.
- **Hardware Monitoring:** The application reads CPU, GPU, and RAM utilization (and, if you turn them on, temperature and power) from your own hardware locally. It **records history only for the hardware figures you have chosen to monitor** in Settings → Hardware, and you can turn hardware recording off entirely with **Settings → Advanced → Record hardware history**. While the Monitor window is open it reads all hardware figures **live** so its tiles and graphs can show them, but anything you are not monitoring is shown only, never recorded. All of it stays on your computer: displayed to you, stored only in the local database described below, and never transmitted.
- **App Activity (optional):** The App Activity window shows which running applications are using the network, using process information from your own computer. This data is the most sensitive the app touches (it can include process names and remote addresses), so it is computed and displayed **live only** - it is **never written to disk, never stored in the history database, and never transmitted**. It also never leaves your machine in a Support Bundle (see below).
- **Configuration File:** Your settings are saved locally on your computer in a `NetSpeedTray_Config.json` file located in your `%appdata%\NetSpeedTray` folder. It contains only your preferences (such as colors, position, and which features are enabled) - no personal data. This file is never transmitted.
- **History Database:** A local SQLite database (`speed_history.db`) is created in the same folder to store your network speed history (per network adapter, by its name), your hardware history (as described above), your connection-latency history, each adapter's error and dropped-packet counts and link speed, when each adapter's link went up or down, and when NetSpeedTray itself was running (start and stop times, with the app version). This data remains on your computer and is never transmitted. It is pruned automatically after the period you set in **Settings → Advanced → Keep history for**.
  - **Backups:** when an upgrade changes the database's format, the previous file is kept beside it as a backup, so you can go back to the older version. A backup holds the history as it was then. If an interrupted upgrade finds an unexpected database file in the way, it moves that file aside instead of deleting it; such a file can hold history too. These are the only files NetSpeedTray treats as history copies, matched by exact name, ignoring upper/lower case as Windows does (each also with a `-wal`, `-shm` or `-journal` ending):
    - `speed_history.db.bak.v<N>_<YYYYMMDD>_<HHMMSS>` (optionally with `_<n>`) - an upgrade's backup; `speed_history.db.bak.v7_...` is the one from the 2.2 upgrade;
    - `speed_history.db.bak` - a backup left by older versions;
    - `speed_history.db.stray_<YYYYMMDD>_<HHMMSS>` (optionally with `_<n>`) - a file an interrupted upgrade moved aside.

    Any other file in the folder - including ones you made yourself, such as `speed_history.db.backup` - is never touched. Each of these is removed once it is older than your **Keep history for** period, and only after NetSpeedTray has itself seen it for 30 days of running time - so a backup is never removed sooner because your computer's clock was wrong or was corrected. A backup is also kept while the clock looks wrong (it jumped, until it has run steadily for a week), and the 2.1 backup is kept for as long as the upgrade that made it has not visibly finished, because then it may be the only copy of your history. A backup that is read-only and linked to another file cannot be removed without changing that other file, so NetSpeedTray leaves it in place and tells you.
  - **Delete all history** (**Settings → Advanced**) erases all of it at once: it is gone from the app immediately, the database file is rewritten so the old data does not linger in it, and every backup and moved-aside file is overwritten and deleted - **including the backup kept from the 2.2 upgrade, so older history can no longer be restored**. That usually finishes straight away; if the Monitor window happens to be reading history at that moment (or another program has a backup open), it completes shortly afterwards, while NetSpeedTray is running, and you are told so. Your settings are kept, and so is the data-usage counter behind the monthly data cap, unless you tick the option to reset it too. That counter keeps, alongside its total, your adapters' names and byte counters at the last save (so traffic while the app was closed can be counted); resetting the counter clears those as well. The counter is only reset if the delete succeeds.

- **Local metrics endpoint (optional):** **Settings → Advanced → Integrations → Local metrics endpoint** is **off by default**. When you turn it on, NetSpeedTray answers `http://127.0.0.1:PORT/metrics` (port 9184 unless you change it) so a tool you run on the same PC - Prometheus, Grafana Alloy and the like - can read your live speeds, data usage, data-cap setting, latency and loss, and (only for what you monitor) CPU/GPU/RAM/VRAM use, plus the NetSpeedTray version number. It listens on the loopback address only, so **no other computer can connect**; it also refuses any connection that is not from this PC and any request that does not name this PC, so a web page you visit cannot read it either. NetSpeedTray **sends nothing anywhere** - it only answers requests from your own machine. The response **includes the names of your network adapters** (which you may have renamed to something personal) as labels; any program running on this PC can read them while the endpoint is on. While it is on, any program on this PC - and any web page you have open, by trying to connect - can tell that the port is open, even though a web page cannot read the answer. Requests from web pages are refused before they count against the endpoint's request limit, but another program on your PC could still use up that limit and slow down a scraper you rely on. The log records when the endpoint starts or stops and on which port, and a warning (without any address) if it ever refuses a connection that is not from this PC. Turn it off and the port closes immediately.

### Support Bundles

NetSpeedTray can generate a "Support Bundle" - a single `.zip` file you can **choose** to attach to a GitHub issue to help diagnose a bug. This file is created locally and is only ever shared if **you** decide to send it.

- **What it contains:** your application logs (including the in-app updater's installer log), your settings file (`config.json`), and basic system info (app version, OS, monitor layout, whether the app runs as administrator, its Windows compatibility flags, and its Task Manager startup state).
- **Logs are scrubbed:** before being added to the bundle, log files are passed through a redaction step that replaces file paths (however they are written, including inside error messages), your Windows username, IP addresses (IPv4 and IPv6), MAC addresses, network-interface GUIDs, and your computer's hostname with placeholders. Network-adapter friendly names (which you may have renamed to something personal) and display device names are replaced, on a best-effort basis, with a **stable placeholder** (e.g. `NIC-1a2b3c4d`) — a one-way hash, so repeated log lines still correlate for debugging but never contain the name itself.
- **What is deliberately left out:** App Activity per-process / per-connection data, your hostname, your Windows username, MAC addresses, and full GPU model strings. Network-interface friendly names never appear verbatim: they are redacted from the bundled settings file and replaced with the stable placeholders described above in logs.
- The bundle includes a `MANIFEST.txt` listing exactly what is and isn't inside, so you can review it before sharing. Nothing is uploaded automatically.

### Update Checking

To check for new versions, NetSpeedTray may periodically contact the GitHub.com API. This is a standard and secure process.

- **Information Sent:** A request is sent to the GitHub API for the NetSpeedTray repository to check for the latest release. As with any internet connection, this request includes basic, non-identifiable information such as your IP address. No personal or user-specific information is added by NetSpeedTray.
- **Information Received:** The response contains public release information - the latest version number, the release notes, and the download links for that release - which is used to tell you an update is available and show you what changed. Choosing to download an update takes you to (or fetches from) the official GitHub Releases page; NetSpeedTray never installs anything without your action.
- **No Personal Data:** No personal or user-specific information is sent during the update check.
